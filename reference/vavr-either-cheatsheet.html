Vavr Either<L,R> — Quick Reference

📖 Reference Document 🔗 Vavr Docs 🔗 Javadoc

Creating

Either<String, Integer> success = Either.right(42);
Either<String, Integer> failure = Either.left("not found");

Core Operations (Right-biased)

MethodWhat it doesOn Left?
map(f) Transforms the Right value: Right(x) → Right(f(x)) Returns self unchanged
flatMap(f) Transforms & flattens: Right(x) → f(x) where f returns Either Returns self unchanged
mapLeft(f) Transforms the Left value: Left(e) → Left(f(e)) Applies f to Left value
fold(onLeft, onRight) Collapses both tracks into a single value Calls onLeft function
peek(f) Runs side effect on Right value, returns self Returns self unchanged
peekLeft(f) Runs side effect on Left value, returns self Calls f on Left value
swap() Swaps Left↔Right: Right(x) → Left(x) Left(e) → Right(e)
getOrElseGet(f) Returns Right value, or applies f to Left Returns f(leftValue)
orElse(other) Returns self if Right, or other if Left Returns other
filterOrElse(p, zero) Keeps Right if predicate passes, else Left(zero) Returns self unchanged

Pipeline Pattern (Railway-Oriented Programming)

// Each step returns Either<Rejection, TradeContext>
Either<Rejection, TradeContext> result =
    validateFormat(event)                     // Step 1
        .flatMap(this::checkDuplicate)       // Step 2 — skipped if Step 1 failed
        .flatMap(this::determineRegion)       // Step 3 — skipped if Step 2 failed
        .flatMap(this::buildSubmission)       // Step 4 — skipped if Step 3 failed
        .peek(sub -> log.info("Created: {}", sub))     // Logging (side effect)
        .peekLeft(rej -> log.warn("Rejected: {}", rej)); // Error logging
Key insight

flatMap is the railway switch. If any step returns Left, all subsequent flatMap calls are skipped — the error rides the Left track to the end. No exceptions. No try-catch. No null checks.

Track Diagram

Right(event) ──▶ validateFormat ──▶ checkDuplicate ──▶ determineRegion ──▶ buildSubmission ──▶ Right(submission) ╲ ╲ ╲ ╲ Left(err) ─────▶ Left(err) ──────▶ Left(err) ───────▶ Left(err) ──▶ Left(rejection)

Converting Between Types

// Try → Either
Try.of(() -> riskyOperation())
   .toEither()                      // Either<Throwable, T>
   .mapLeft(Throwable::getMessage);  // Either<String, T>

// Option → Either
Option.of(maybeNull)
   .toEither("Value was null");       // Either<String, T>

// Either → fold to a single type
String message = result.fold(
    rej -> "Rejected: " + rej.reason(),
    sub -> "Submitted: " + sub.id()
);

Testing Either Values

// JUnit 5 assertions for Either
assertThat(result.isRight()).isTrue();
assertThat(result.get()).isEqualTo(expectedSubmission);

assertThat(result.isLeft()).isTrue();
assertThat(result.getLeft()).isEqualTo(expectedRejection);

// Pattern: extract and assert
result.peek(submission -> {
    assertThat(submission.getRegion()).isEqualTo("EMIR");
    assertThat(submission.getTradeId()).isNotNull();
});

Common Pitfalls

Watch out
  • Using get() without checking isRight() — throws NoSuchElementException on Left
  • Using map when you need flatMap — creates nested Either<L, Either<L, R>>
  • Performing side effects inside map — use peek instead to keep map pure
  • Forgetting that Either is right-biased — map ignores Left values
