🔨 Hands-On Exercises & Projects

📋 27 exercises across 5 weeks 🏗️ 4 progressive build milestones 🏆 1 capstone project

Every exercise is self-contained — you create the project yourself, write the code, and verify against the acceptance criteria listed. The exercises progressively build toward the Week 5 capstone: a mini trade reporting engine that mirrors Exgester's real architecture.

How this works

Each exercise tells you what to build and how to verify it. You write the code. If you get stuck, use /teach and describe the exercise — I'll guide you without giving you the answer.

Progressive Build Strategy

Weeks 1–2 use standalone Java files (no Spring). Week 3 onward, you create a Spring Boot Maven project and keep growing it. By Week 5, it's a working mini-Exgester.

Week 1 Java Foundations & Functional Thinking

All exercises this week are standalone Java files. Create a folder week1/ in your workspace and write/run each exercise there with javac + java or your IDE.

E1 · SOLID Trade Refactor Starter

Day 1 · ~45 min

You are given a single TradeProcessor class that does everything: validates a trade, checks region, builds a message, and logs. It violates SRP, OCP, and DIP.

Your task: Refactor it into separate classes following SOLID. Create at least 4 classes: TradeValidator, RegionDeterminer, MessageBuilder, and TradeProcessor that composes them.

Starter code you write first (the "bad" version):

// TradeProcessor.java — the monolith public class TradeProcessor { public String process(String tradeId, String type, double notional, String region) { // validation if (tradeId == null || tradeId.isEmpty()) return "ERROR: no trade ID"; if (notional <= 0) return "ERROR: invalid notional"; // region logic String reportingRegion; if (region.equals("EU")) reportingRegion = "EMIR"; else if (region.equals("US")) reportingRegion = "CFTC"; else if (region.equals("AU")) reportingRegion = "ASIC"; else return "ERROR: unknown region"; // build message String message = reportingRegion + "|" + tradeId + "|" + type + "|" + notional; System.out.println("Processed: " + message); return message; } }

Acceptance Criteria:

  • ☐ No class has more than one reason to change
  • ☐ Adding a new region (e.g. FCA) requires NO modification to existing classes
  • ☐ TradeProcessor depends on interfaces, not concrete classes
  • ☐ You can explain which SOLID principle each refactoring addresses

E2 · Generic DecisionStep Interface Intermediate

Day 2 · ~60 min

Build: A generic DecisionStep<I, O> interface with a single method O execute(I input). Then create 3 concrete implementations that chain together:

  • ParseStep — takes String → returns TradeEvent
  • ValidateStep — takes TradeEvent → returns ValidatedTrade
  • EnrichStep — takes ValidatedTrade → returns EnrichedTrade

Then write a Pipeline class that chains them: String → TradeEvent → ValidatedTrade → EnrichedTrade.

Stretch: Add a wildcard method addStep(DecisionStep<? super T, ? extends R>).

Acceptance Criteria:

  • ☐ Pipeline compiles and runs without raw types or unchecked casts
  • ☐ Each step is independently testable
  • ☐ You can explain why ? super T and ? extends R are needed

E3 · Lambda Trade Filter Starter

Day 3 · ~45 min

Build: Create a TradeEvent record/class with fields: tradeId, assetClass, notional, region, counterpartyLei. Then create a TradeFilterService that accepts a List<Predicate<TradeEvent>> and applies them all.

Write these filters as lambdas:

  • Notional above threshold (configurable)
  • Asset class is in allowed set {"IR", "FX", "CR"}
  • Counterparty LEI is not blank
  • Region is known

Acceptance Criteria:

  • ☐ No filter logic is inside TradeFilterService — all passed as lambdas
  • ☐ Filters are composed with Predicate.and()
  • ☐ A main() method tests with 10 sample trades, printing which pass and fail

E5 · Immutable Trade Domain Model Starter

Day 5 · ~45 min

Build: Create the full immutable domain model you'll reuse for the rest of the course:

TradeEvent — the raw inbound event (immutable) TradeContext — enriched event with region + metadata (immutable) RejectionReason — value object: code + message (immutable) SubmissionMessage — the outbound regulatory message (immutable, builder pattern)

Use manual immutability (final fields, no setters, constructor-only). Later in Week 4, you'll convert these to Lombok @Value.

Acceptance Criteria:

E6 · Composable Validation Pipeline Intermediate

Day 6 · ~60 min

Build: Using Function.andThen() and Predicate.and(), compose a validation pipeline from 4 independent validators. Each validator is a Function<TradeEvent, Optional<String>> that returns Optional.empty() on success or Optional.of("error message") on failure.

Then build a CompositeValidator that runs all validators and collects all errors (not just the first).

Acceptance Criteria:

  • ☐ 4 validators: notional > 0, region not blank, tradeId matches pattern, assetClass in allowed set
  • ☐ CompositeValidator returns List<String> of all errors, or empty list on success
  • ☐ Adding a 5th validator requires only 1 line change
  • ☐ Test with a trade event that fails 3 out of 4 validators — all 3 errors must be collected

Week 2 Vavr & Railway-Oriented Programming

Still standalone Java, but now add Vavr as a dependency. Create a week2/ Maven project with just the Vavr dependency. Reuse your domain model from Week 1.

E7 · Try-Wrapping Risky Code Starter

Day 8 · ~45 min

Build: A TradeEventParser that parses JSON strings into TradeEvent objects. The parser can fail (bad JSON, missing fields). Wrap it with Vavr Try.

// 5 test inputs: String valid = "{\"tradeId\":\"T-001\", \"assetClass\":\"IR\", ...}"; String badJson = "not json at all"; String missing = "{\"tradeId\":\"T-002\"}"; // missing required fields String nullVal = null; String empty = "";

Acceptance Criteria:

  • ☐ TradeEventParser.parse(String) returns Try<TradeEvent>
  • ☐ No try-catch blocks in your code — all exception handling via Try
  • ☐ Convert each Try to Either<String, TradeEvent> using .toEither().mapLeft(Throwable::getMessage)
  • ☐ All 5 inputs handled gracefully, success and failure paths printed

E8 · Either Fundamentals Kata Starter

Day 9 · ~60 min

Build: A series of small functions, each returning Either<String, T>. Practice every core operation:

// Write each of these, test each independently: Either<String, Integer> parseInt(String s) // Left if not a number Either<String, Integer> ensurePositive(Integer n) // Left if <= 0 Either<String, Double> divide(Integer a, Integer b) // Left if b == 0 Either<String, String> classify(Double result) // "small"/"medium"/"large" // Then chain them: String input = "42"; Either<String, String> result = parseInt(input) .flatMap(n -> ensurePositive(n)) .flatMap(n -> divide(100, n)) .map(d -> classify(d));

Test with inputs: "42", "-5", "0", "abc", "100". Trace the track for each.

Acceptance Criteria:

  • ☐ Each function returns Either, not throwing exceptions
  • ☐ For each input, you can explain on paper which track it takes at each step
  • ☐ You demonstrate fold() to collapse the final result into a single output string
  • ☐ You demonstrate mapLeft() to enrich error messages with step info

🏗️ E9 · First Decision Pipeline Intermediate

Day 10 · ~90 min — THE MOST IMPORTANT EXERCISE

Build: A 4-step trade decision pipeline using Either<RejectionReason, TradeContext>:

Step 1: validateFormat(TradeEvent) → Either<RejectionReason, TradeEvent> Step 2: checkDuplicate(TradeEvent) → Either<RejectionReason, TradeEvent> Step 3: determineRegion(TradeEvent) → Either<RejectionReason, TradeContext> Step 4: buildSubmission(TradeContext) → Either<RejectionReason, SubmissionMessage> // The pipeline: public Either<RejectionReason, SubmissionMessage> process(TradeEvent event) { return validateFormat(event) .flatMap(this::checkDuplicate) .flatMap(this::determineRegion) .flatMap(this::buildSubmission); }

Test with these scenarios:

  • Valid trade for EU region → Should produce an EMIR SubmissionMessage (Right track all the way)
  • Trade with blank ID → Should fail at Step 1 with INVALID_FORMAT
  • Duplicate trade → Should fail at Step 2 with DUPLICATE
  • Trade with unknown region "XX" → Should fail at Step 3 with UNKNOWN_REGION

Acceptance Criteria:

  • ☐ Pipeline uses only flatMap chaining — no if/else, no try/catch
  • ☐ Failure at any step short-circuits remaining steps (proven by adding prints)
  • ☐ RejectionReason carries both a code enum and a human-readable message
  • ☐ You can draw the two-track diagram on paper for each test case

E10 · Pipeline Enhancements Intermediate

Day 11 · ~60 min

Enhance E9's pipeline with:

  • peek() — add audit logging after each successful step (print to console)
  • peekLeft() — add rejection logging
  • mapLeft() — enrich rejection reasons with timestamps and step names
  • filterOrElse() — add a notional threshold check: reject if notional < 1000

Acceptance Criteria:

  • ☐ Console shows audit trail: "Step 1 passed → Step 2 passed → ..." for success
  • ☐ Console shows rejection point: "Step 1 passed → Step 2 REJECTED: DUPLICATE" for failure
  • ☐ Rejection reasons include the step name where failure occurred
  • ☐ Side effects (logging) don't alter the pipeline's return value

E11 · Tuple Routing & Pattern Matching Intermediate

Day 12 · ~60 min

Build: Extend your pipeline so that after determineRegion, the trade is routed to different sub-pipelines based on region. Use Tuple2<TradeContext, RegulatoryRegion> to carry both values, and Vavr Match to branch.

// After determining region, route: .flatMap(ctx -> Match(ctx.getRegion()).of( Case($("EMIR"), () -> buildEmirSubmission(ctx)), Case($("CFTC"), () -> buildCftcSubmission(ctx)), Case($("ASIC"), () -> buildAsicSubmission(ctx)), Case($(), () -> Either.left(new RejectionReason("UNSUPPORTED_REGION"))) ))

Acceptance Criteria:

  • ☐ Each region produces a differently-structured SubmissionMessage
  • ☐ Unknown regions are handled by the default case without throwing
  • ☐ At least one sub-pipeline uses Tuple2 to carry extra context

E12 · Pure Core, Imperative Shell Intermediate

Day 13 · ~60 min

Refactor E9-E11: Separate your code into two layers:

// PURE CORE — no I/O, no side effects, no mutable state DecisionPipeline.java → all Either logic, stateless, testable with simple data // IMPERATIVE SHELL — all the messy I/O TradeEventListener.java → reads from console/file, calls pipeline, prints results

Acceptance Criteria:

  • ☐ DecisionPipeline has ZERO System.out.println calls (except via peek callbacks)
  • ☐ DecisionPipeline takes no I/O dependencies — only data in, data out
  • ☐ All console I/O lives in the shell layer
  • ☐ You can unit-test DecisionPipeline without mocking any I/O
