🔨 Hands-On Exercises (Deep Dive)

This document contains the specifications and acceptance criteria for all build exercises. In the enterprise Exgester module, there are no shortcuts. Your code must strictly adhere to the functional principles taught.

The Honor System

Don't check off an acceptance criteria until your code actually does it. You are verifying your own work.

DAY 1 Deeply Immutable Trade Domain Model

In Exgester, the Trade object is passed through dozens of steps. It must be absolutely immutable to prevent accidental data corruption across JMS threads.

Specification

Create a sealed interface TradeEvent permitting exactly 3 records: NewTrade, AmendTrade, and CancelTrade. Ensure deep immutability using Java 10+ List.copyOf() in compact constructors.

Acceptance Criteria
  • TradeEvent is a sealed interface permitting only the 3 specific records.
  • NewTrade has a compact constructor that intercepts the parties List and reassigns it via List.copyOf(parties) to prevent shallow immutability traps.
  • NewTrade has a "Wither" method: withRegion(String region) returning a new record instance.
  • No reflection or setter-based instantiation is used.
DAY 2 Safe Parsing & Context Tuples

Data from external sources is untrustworthy. You must parse it safely without throwing runtime exceptions that crash our threads.

Specification

Using com.fasterxml.jackson.databind.ObjectMapper (with VavrModule registered) and Vavr's Try, write a class TradeParser.

Acceptance Criteria
  • Calling parseTrade(String json) returns a Try<NewTrade>.
  • Use .recover() to map a JsonParseException into a default dummy NewTrade for testing, but let IllegalArgumentException propagate as a Failure.
  • Write a method buildContext(NewTrade trade) that calculates a hash of the trade and returns a Tuple2<NewTrade, String> (the trade and its hash).
  • Vavr's Option<String> is used correctly in the domain model for optional JSON fields instead of java.util.Optional.
DAY 3 Strongly Typed ROP
Specification

Create a class TradeValidator. Instead of returning Either<String, Trade>, you must return Either<Rejection, NewTrade> where Rejection is a custom Java 17 Record containing a fault code, message, and the offending Trade.

Acceptance Criteria
  • Create the Rejection(String code, String msg, NewTrade payload) record.
  • Write validateLei(NewTrade trade). Returns Either.right(trade) if LEI exists, else Either.left(new Rejection(...)).
  • Implement a process(String json) method that parses the JSON, validates it, and uses fold() at the end to print either "Sent to DLQ: [Rejection]" or "Sent downstream: [Trade]".
DAY 4 Side Effects & Strategy Mapping
Specification

We need to extract our validation pipeline into a Strategy map so we can route trades differently based on their Region.

Acceptance Criteria
  • Create an interface RegionStrategy extends Function<NewTrade, Either<Rejection, NewTrade>>.
  • Implement EmirStrategy and AsicStrategy. Chain multiple validations in each using flatMap.
  • Use .peek() to log a simulated metric whenever a validation step successfully passes.
  • In your main engine, use a Map<String, RegionStrategy> to look up the correct pipeline and execute it dynamically.
