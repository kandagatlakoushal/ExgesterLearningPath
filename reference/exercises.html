🔨 Hands-On Exercises

This document contains the specifications and acceptance criteria for all build exercises in the 4-week Exgester Mastery curriculum.

The Honor System

Don't check off an acceptance criteria until your code actually does it. You are verifying your own work.

DAY 1 Trade Domain Model

In Exgester, the Trade object is passed through dozens of steps. It must be absolutely immutable to prevent accidental data corruption.

Specification

Create a pure Java project (no Spring yet). Implement a Trade class and a Counterparty class.

  • Trade fields: tradeId (String), notional (Double), region (String), parties (List of Counterparty)
  • Counterparty fields: lei (String), role (String)

Make both classes 100% immutable. Provide a withRegion(String region) method on Trade that returns a new Trade instance with the updated region.

Acceptance Criteria
  • All classes are final.
  • All fields are private final.
  • There are NO setter methods.
  • The constructor makes a defensive copy of the parties list (e.g., using List.copyOf() or Collections.unmodifiableList()).
  • Calling getParties() returns an unmodifiable list.
  • Calling trade.withRegion("EMIR") returns a completely new Trade instance with identical fields except the region.

DAY 2 Safe Trade Parser

Data from external sources is untrustworthy. You must parse it safely without throwing runtime exceptions that crash our threads.

Specification

Using com.fasterxml.jackson.databind.ObjectMapper and Vavr's Try, write a class TradeParser with a method Try<Trade> parseTrade(String json).

Also, write a method Tuple2<String, Double> extractSummary(Trade trade) that returns the Trade ID and Notional amount as a Tuple.

Acceptance Criteria
  • Calling parseTrade with valid JSON returns Try.Success containing a populated Trade object.
  • Calling parseTrade with invalid/malformed JSON returns Try.Failure containing the exception. It does not throw an exception.
  • Calling extractSummary returns a Vavr Tuple2 with the correct fields.
DAY 3 First Either Validation
Specification

Create a class TradeValidator. Write a method Either<String, Trade> validateLei(Trade trade). If the Trade's Counterparty LEI is blank or null, return a Left with the error message "Missing LEI". Otherwise, return a Right with the trade.

Acceptance Criteria
  • Method returns Either.right(trade) for a trade with a valid LEI.
  • Method returns Either.left("Missing LEI") for a trade with no LEI.
DAY 4 Composable Pipeline Steps
Specification

Add 4 more validation methods to TradeValidator (e.g., validateNotional, validateRegion). Then, create a method Either<String, Trade> process(Trade trade) that chains them all together using flatMap.

Acceptance Criteria
  • The process method contains exactly one return statement and chains multiple methods using .flatMap(this::validate...).
  • If the first validation fails, the subsequent validations are never executed.
  • If all validations pass, a Right is returned.
