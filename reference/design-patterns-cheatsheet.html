Design Patterns in Exgester — Quick Reference

📖 Reference Document 🔗 Refactoring.Guru

Strategy — Swappable Algorithms

// Interface defines the contract
public interface ReportabilityStrategy {
    Either<Rejection, Boolean> isReportable(TradeEvent event);
}

// Each regulatory region has its own implementation
@Service @Profile("emir")
public class EmirReportability implements ReportabilityStrategy { ... }

@Service @Profile("cftc")
public class CftcReportability implements ReportabilityStrategy { ... }

// Consumer doesn't know which strategy it got
@Service
public class DecisionEngine {
    private final ReportabilityStrategy strategy; // injected by Spring
}

When you see it in Exgester: Different reporting rules per regulatory region, injected via Spring profiles.

Factory — Object Creation Without Exposure

public class SubmissionMessageFactory {
    public static SubmissionMessage create(RegulatoryRegion region, TradeContext ctx) {
        return switch (region) {
            case EMIR  -> new EmirSubmission(ctx);
            case CFTC  -> new CftcSubmission(ctx);
            case ASIC  -> new AsicSubmission(ctx);
            case FCA   -> new FcaSubmission(ctx);
        };
    }
}

When you see it in Exgester: Constructing the right submission message type based on which regulatory region a trade is reported to.

Template Method — Skeleton with Overridable Steps

public abstract class AbstractReportingFlow {

    // The template — fixed algorithm skeleton
    public final Either<Rejection, SubmissionMessage> process(TradeEvent event) {
        return validate(event)
            .flatMap(this::enrich)       // hook — subclasses override
            .flatMap(this::applyRules)    // hook — subclasses override
            .flatMap(this::format);       // hook — subclasses override
    }

    // Common step — not overridable
    private Either<Rejection, TradeEvent> validate(TradeEvent e) { ... }

    // Hooks — subclasses provide client-specific logic
    protected abstract Either<Rejection, TradeContext> enrich(TradeEvent e);
    protected abstract Either<Rejection, TradeContext> applyRules(TradeContext ctx);
    protected abstract Either<Rejection, SubmissionMessage> format(TradeContext ctx);
}

@Service @Profile("anz")
public class AnzReportingFlow extends AbstractReportingFlow {
    @Override protected Either<...> enrich(...) { /* ANZ logic */ }
    @Override protected Either<...> applyRules(...) { /* ANZ rules */ }
    @Override protected Either<...> format(...) { /* ANZ format */ }
}

When you see it in Exgester: A common reporting flow where the high-level steps are fixed but each client provides different implementations.

Chain of Responsibility — Sequential Decision Handlers

public interface DecisionHandler {
    Either<Rejection, TradeContext> handle(TradeContext ctx);
}

// Each handler in the chain
public class DuplicateCheckHandler implements DecisionHandler { ... }
public class RegionDeterminationHandler implements DecisionHandler { ... }
public class ThresholdCheckHandler implements DecisionHandler { ... }

// Composed via flatMap — this IS the chain
List<DecisionHandler> handlers = List.of(dupCheck, regionCheck, thresholdCheck);

Either<Rejection, TradeContext> result = handlers
    .stream()
    .reduce(
        Either.right(initialCtx),
        (either, handler) -> either.flatMap(handler::handle),
        (a, b) -> a  // combiner (unused in sequential stream)
    );

When you see it in Exgester: Decision pipeline steps — each step in the chain can accept, reject, or enrich the trade context.

Composite — Trees of Rules

public interface ReportabilityRule {
    boolean matches(TradeEvent event);
}

// Leaf rules
public class AssetClassRule implements ReportabilityRule { ... }
public class NotionalThresholdRule implements ReportabilityRule { ... }

// Composite rule — treats children uniformly
public class AllOfRule implements ReportabilityRule {
    private final List<ReportabilityRule> children;

    public boolean matches(TradeEvent event) {
        return children.stream().allMatch(r -> r.matches(event));
    }
}

public class AnyOfRule implements ReportabilityRule {
    private final List<ReportabilityRule> children;

    public boolean matches(TradeEvent event) {
        return children.stream().anyMatch(r -> r.matches(event));
    }
}

When you see it in Exgester: Complex reportability rules composed from simpler sub-rules using AND/OR logic.

Builder — Complex Object Construction

@Value
@Builder
public class EmirSubmission {
    String tradeId;
    String counterpartyLei;
    String assetClass;
    BigDecimal notionalAmount;
    String currency;
    LocalDate executionDate;
    LocalDate maturityDate;
    String uti;           // Unique Transaction Identifier
    String reportingSide;
}

// Usage
EmirSubmission submission = EmirSubmission.builder()
    .tradeId("T-12345")
    .counterpartyLei("5493001KJTIIGC8Y1R12")
    .assetClass("IR")
    .notionalAmount(new BigDecimal("1000000"))
    .currency("USD")
    .executionDate(LocalDate.of(2024, 1, 15))
    .build();

When you see it in Exgester: Building submission messages with many fields, often via Lombok @Builder.
