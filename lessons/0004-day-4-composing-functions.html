Day 4: Advanced Pipeline Composition

By now, you understand the basics of flatMap for chaining Either. But enterprise systems require more than just a linear chain. We need to handle side-effects (like logging or metrics), integration with asynchronous operations, and accumulating multiple errors simultaneously.

1. Managing Side Effects with peek

In functional programming, functions should be pure (no side effects). However, in the real world, we must write logs, increment Prometheus metrics, or trigger audit events. Vavr provides peek and peekLeft for this exact purpose. They allow you to execute a side-effect without modifying the data inside the pipeline.


public Either<Rejection, Trade> process(Trade rawTrade) {
    return validateId(rawTrade)
        .peek(trade -> metrics.increment("validation.id.success"))
        .flatMap(this::validateNotional)
        .peekLeft(rejection -> log.warn("Trade rejected: {}", rejection.code()));
}

2. Either vs. Validation (Fast-Fail vs. Error Accumulation)

Either.flatMap is a fast-fail mechanism. If a trade has a missing ID and a bad Notional, Either will fail at the ID check, and the Notional check will never run. The user only sees one error at a time.

If you need to validate a trade and return all errors at once (e.g., for a REST API response), you must use Vavr's Validation monad instead of Either. Validation is an applicative functor designed for accumulating errors.


import io.vavr.control.Validation;

// Combining independent validations
Validation<Seq<String>, Trade> validTrade = Validation.combine(
    validateIdAcc(trade),
    validateNotionalAcc(trade),
    validateRegionAcc(trade)
).ap((id, notional, region) -> trade); // Only runs if ALL are valid

Exgester primarily uses Either because our processing is strictly sequential and fast-failing saves compute resources, but Validation is used at the API gateway layer.

3. Bridging to the Imperative World: sequence

What if you receive a List<Trade> and process them, resulting in a List<Either<Rejection, Trade>>? Working with a list of Eithers is painful. You usually want an Either<Seq<Rejection>, List<Trade>> (i.e., flip the containers).

Vavr's Either.sequence() flips the types:


List<Either<Rejection, Trade>> results = trades.stream()
    .map(this::processTrade)
    .toList();

// Flip to Either<Seq<Rejection>, Seq<Trade>>
// If ANY trade failed, sequence() returns a Left containing the FIRST failure.
// If ALL passed, it returns a Right containing a list of ALL valid trades.
Either<Rejection, Seq<Trade>> batchResult = Either.sequence(results);

4. Extracting the "Strategy" Pattern

In Exgester, different regions (EMIR, ASIC) require different validation pipelines. Instead of a massive switch statement, we define pipelines as Function<Trade, Either<Rejection, Trade>> and register them in a Spring Context via the Strategy Pattern.


@Component
public class EmirValidator implements Function<Trade, Either<Rejection, Trade>> {
    @Override
    public Either<Rejection, Trade> apply(Trade trade) {
        return validateEmirFields(trade).flatMap(this::checkEmirLimits);
    }
}
