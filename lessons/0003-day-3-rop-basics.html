Day 3: Enterprise Railway-Oriented Programming (ROP)

In Exgester, a single trade event must pass through routing logic, regulatory determination, data enrichment, and validation before it is converted to a Regulatory Submission Message. In a legacy Java application, this results in the "Arrow Anti-Pattern"—deeply nested if-else blocks or a chaotic web of custom exceptions. Railway-Oriented Programming (ROP) standardizes this into a linear pipeline.

1. The Two-Track Model and Vavr Either

Think of Either<L, R> as a railway switch. The Right track is the happy path (computation continues). The Left track is the error/rejection path. Once a trade is switched to the Left track, it bypasses all subsequent Right switches.

Type Signatures in Exgester

In our architecture, the Left type is rarely just a String. It is usually a strongly-typed DomainError enum or record, capturing exactly why a trade was rejected so it can be routed to a Dead Letter Queue (DLQ) for operations to review.


public record Rejection(String code, String reason, Trade payload) {}

// A validation function signature
public Either<Rejection, Trade> validateCounterparty(Trade trade) {
    if (trade.lei() == null || trade.lei().isBlank()) {
        return Either.left(new Rejection("MISSING_LEI", "Counterparty LEI is required", trade));
    }
    return Either.right(trade);
}

2. The Bias of Either

Vavr's Either is "Right-biased." This means operations like map and flatMap only apply to the Right side. If the Either is a Left, calling map does absolutely nothing—it just returns the Left as-is.


Either<Rejection, Trade> validTrade = Either.right(new Trade("T1", 100.0));
Either<Rejection, Trade> invalidTrade = Either.left(new Rejection("ERR", "Bad", null));

// map applies ONLY to the Right.
Either<Rejection, Double> notional1 = validTrade.map(Trade::notional); // Right(100.0)
Either<Rejection, Double> notional2 = invalidTrade.map(Trade::notional); // Left(Rejection)

3. Escaping the Monad: fold()

Eventually, the railway must end. We must take our Either<L, R> and convert it into a final output (e.g., a Spring REST Response, or a JMS Message payload). You do this using fold().

fold takes two functions: one that handles the Left, and one that handles the Right. It forces the developer to handle both outcomes at compile-time.


public void processIncomingMessage(String json) {
    Either<Rejection, Trade> pipelineResult = parseTrade(json) // Returns Either
        .flatMap(this::validateCounterparty)
        .flatMap(this::checkLimits);

    // Terminal operation: fold unwraps the Either safely
    pipelineResult.fold(
        rejection -> dlqSender.send(rejection), // The Left Path
        validTrade -> downstreamSender.send(validTrade) // The Right Path
    );
}
Compile-Time Safety

Because fold requires you to provide logic for both the success and error states, you can never accidentally "forget" to handle an error. This completely eliminates a massive class of production bugs.
