Day 1: Enterprise Immutability & Java 17

Welcome to Day 1 of Exgester Mastery. In an event-driven system processing thousands of trades per second across multi-threaded asynchronous consumers (JMS listeners), state mutation is the enemy of predictability. Exgester relies on strict immutability to guarantee thread safety without the performance bottleneck of synchronized locks.

The Threading Context in Exgester

When an AMQ message arrives, Spring spins up a listener thread. That thread parses the JSON and passes the resulting Trade object through a Vavr Either pipeline. If any step mutates the trade (e.g., normalizes a currency code in-place), you lose the audit trail. If the trade is passed to an asynchronous CompletableFuture for external reference data lookup, an in-place mutation will cause a catastrophic race condition.

1. Java 17 Records vs. Boilerplate POJOs

Historically, achieving immutability in Java required massive boilerplate: private final fields, a constructor assigning all fields, no setters, and verbose equals(), hashCode(), and toString() methods. While Lombok's @Value helped, Java 17 native Records are superior for domain modeling.


// ✅ Native Java 17 Record
public record Trade(
    String tradeId, 
    String region, 
    double notional,
    List<Counterparty> parties
) {
    // Records automatically generate getters, equals, hashCode, and toString.
}

The JVM Semantics of Records

Unlike regular classes, records have special JVM-level semantics. They are transparent carriers of immutable data. Serialization frameworks (like Jackson) can deserialize them without needing a no-arg constructor, bypassing the reflection hacks required for standard POJOs. This is critical for Exgester's JMS message parsing.

2. The Trap of Shallow Immutability

A record guarantees that its references cannot be reassigned. It does not guarantee that the objects being referenced are immutable. This is the "Shallow Immutability Trap."


public record Trade(String tradeId, List<String> tags) {}

// ❌ DANGEROUS: The list reference is final, but the list contents are mutable!
List<String> mutableTags = new ArrayList<>();
mutableTags.add("EMIR");
Trade myTrade = new Trade("T1", mutableTags);

mutableTags.add("ASIC"); // myTrade now has "ASIC" too! Thread-safety broken.

Defensive Copying in Record Constructors

To achieve Deep Immutability, you must intercept the record's compact constructor and enforce immutability on collection types using List.copyOf() (introduced in Java 10, significantly safer than Collections.unmodifiableList() because it guarantees no underlying mutable reference exists).


public record Trade(String tradeId, List<String> tags) {
    // Compact constructor - executes during instantiation
    public Trade {
        // Requires Java 10+. Creates a truly unmodifiable copy.
        // If 'tags' is already an unmodifiable List, it avoids copying.
        tags = tags == null ? List.of() : List.copyOf(tags);
    }
}

3. Wither Methods for State Transitions

In Exgester, a trade might undergo normalization (e.g., converting a legacy client ID to a standardized LEI). Since we can't mutate the record, we use "Wither" methods. A Wither method returns a completely new instance with one specific field changed, copying the rest.


public record Trade(String tradeId, String region, double notional) {
    
    // The "Wither" pattern
    public Trade withRegion(String newRegion) {
        return new Trade(
            this.tradeId,
            newRegion,
            this.notional
        );
    }
}

Note: While Lombok provides @With, understanding the mechanical allocation underneath is vital. Creating new objects creates garbage collection (GC) pressure. However, the modern JVM (especially G1GC and ZGC) is highly optimized for short-lived object allocation (Eden space). The cost of allocation is far outweighed by the safety of lock-free thread semantics.

4. Sealing the Domain Hierarchy

Exgester processes multiple types of events: NewTrade, AmendTrade, and CancelTrade. Instead of relying on a fragile String actionType field, we use Java 17 Sealed Classes to strictly define the domain hierarchy. This forces exhaustive pattern matching downstream.


// The domain is locked. No one can create an unexpected TradeEvent subclass.
public sealed interface TradeEvent permits NewTrade, AmendTrade, CancelTrade {}

public record NewTrade(String id, double notional) implements TradeEvent {}
public record AmendTrade(String id, double delta) implements TradeEvent {}
public record CancelTrade(String id, String reason) implements TradeEvent {}
