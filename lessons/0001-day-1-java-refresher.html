Day 1: Java 11+ Refresher & Immutability

Welcome to Day 1 of Exgester Mastery. Before we dive into Railway-Oriented Programming and Spring profiles, we must ensure our foundational Java skills are solid. The Exgester codebase relies heavily on modern Java idioms to keep complex data transformations safe.

Today, we will focus on the most important concept in data-heavy pipelines: Immutability.

The Exgester Context

In Exgester, a trade event passes through dozens of decision steps. If one step modifies the trade object in place (mutability), it becomes impossible to reason about what the trade looked like at the start of the pipeline vs the end. Bugs become untraceable.

1. The Power of Immutability

An immutable object cannot be changed after it is constructed. To "change" an immutable object, you must create a new instance with the updated values.

The Anti-Pattern: Mutable POJO


// ❌ BAD: Mutable
public class Trade {
    private String tradeId;
    private String status;
    
    // Setters allow anyone to modify the state at any time
    public void setStatus(String status) {
        this.status = status;
    }
}

The Solution: Immutable Value Object


// ✅ GOOD: Immutable with Java 17 Records
public record Trade(String tradeId, String status) {
    
    // To change status, return a new copy
    public Trade withStatus(String newStatus) {
        return new Trade(this.tradeId, newStatus);
    }
}

2. Optional: Banishing NullPointerExceptions

Exgester pipelines are allergic to null. When you look up a region config, or parse an optional XML field, you must use Optional to signal to the caller that the value might be missing.


// ❌ BAD: Returns null
public String getLei(Trade trade) {
    if (trade.getCounterparty() != null) {
        return trade.getCounterparty().getLei();
    }
    return null; // A crash waiting to happen downstream
}

// ✅ GOOD: Returns Optional
public Optional<String> getLei(Trade trade) {
    return Optional.ofNullable(trade.getCounterparty())
                   .map(Counterparty::getLei);
}

3. Streams & Lambdas

Declarative data processing is key. Instead of for loops that mutate a list, we use Streams to map and filter data.


// Find all trades that need EMIR reporting
List<Trade> emirTrades = trades.stream()
    .filter(t -> "EMIR".equals(t.getRegion()))
    .filter(t -> t.getNotional() > 10000)
    .collect(Collectors.toList());
